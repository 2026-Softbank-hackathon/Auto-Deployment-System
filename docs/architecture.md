- 6장에서 먼저 검증할 PoC와 일정을 확인해요.

# 2. 핵심 설계 개념

## 2.1 컨트롤 플레인과 데이터 플레인 분리

배포를 지휘하는 곳(컨트롤 플레인)과 앱이 실행되는 곳(데이터 플레인)을 나눠요. 컨트롤 플레인이 멈춰도 배포된 앱은 계속 동작하고, 새 환경은 데이터 플레인 하나를 추가하는 것으로 지원해요. (NFR-06·07)

## 2.2 IR (앱 명세)

사용자 앱을 클라우드 중립적인 설계도(IR)로 먼저 바꿔요. IR에는 "무엇이 필요한가"만 있고 "어떻게 만들까"는 없어요. 모든 환경이 같은 IR을 입력으로 받기 때문에 환경 차이 흡수와 이식성이 구조로 보장돼요. (IR-01~05, NFR-01)

## 2.3 프로바이더 어댑터

IR을 실제 리소스로 바꾸는 코드는 환경마다 따로 둬요. 클라우드 고유 기능(트래픽 분할, 관리형 시크릿 등)은 어댑터 안과 IR의 환경별 오버라이드로 수용해요. 관측 게이트웨이도 같은 어댑터 패턴을 써요. (PRV-03~07, NFR-09)

## 2.4 승인 게이트와 락

코드 수정과 인프라 변경은 반드시 사람 승인을 거쳐요. 같은 환경에는 한 번에 하나의 배포만 실행되도록 오케스트레이터가 환경 단위 락을 관리하고, IaC state도 따로 잠가요. (PAT-07, PRV-02, LCK-01·03, NFR-02)

## 2.5 AI는 API 클라이언트

AI 에이전트는 시스템 한가운데가 아니라 CLI·웹과 같은 층의 클라이언트예요. AI가 무엇을 하든 API를 거치므로 승인, 락, 이력이 자동으로 적용돼요. AI는 판단이 필요한 단계에만 쓰고 실행은 검증된 코드가 맡아요. (AGT-04, NFR-08)

# 3. 프로젝트 구조

컴포넌트 하나가 폴더 하나이자 실행 단위 하나가 되도록 나눴어요. 컴포넌트끼리는 코드를 직접 공유하지 않고, packages에 정의된 계약(타입과 스키마)으로만 소통해요.

## 3.1 리포지토리 구조 (모노레포)

## 3.2 실행 단위 (컨트롤 플레인 Compose 서비스)

| **서비스** | **개수** | **비고** |
| --- | --- | --- |
| api | N | 무상태. 로드밸런서 뒤에서 여러 개 실행 |
| orchestrator | 1 (대기 1) | 상태는 Postgres에 있으므로 장애 시 대기 인스턴스가 이어받음 |
| worker-analyzer | N | LLM 호출 포함 |
| worker-builder | N | 샌드박스(루트리스 BuildKit) 안에서 빌드 |
| worker-provisioner | N | IaC 엔진 실행, 클라우드 API 호출 |

| agent | 1~N | LLM 호출, 토큰 기록 |
| obs-gateway | 1~N | 무상태 조회 서비스 |
| recommender | 1 | 규칙 엔진 + 가격 카탈로그 |
| web | 1~N | Next.js |
| postgres · redis · minio · registry | 각 1 | 데모는 컨테이너, 운영은 관리형 서비스로 교체 가능 |

온프레미스 에이전트와 CLI는 컨트롤 플레인 밖에서 실행돼요. 에이전트는 사용자 서버에, CLI는 개발자 PC에 설치해요.

## 3.3 모듈 경계 원칙

- 워커와 오케스트레이터는 contracts의 메시지 타입으로만 소통해요. 서로의 내부 코드를 import하지 않아요.

- 클라우드별 코드는 packages/adapters와 obs-adapters 안에만 있어요. 새 환경 추가 = 어댑터 폴더 추가예요.

- Postgres 테이블은 소유 컴포넌트가 정해져 있어요. 예를 들어 deployments는 오케스트레이터만 씁니다.

- IR 스키마는 한 곳(ir-schema)에서 정의하고, 분석·추천·프로비저닝·웹이 모두 같은 검증기를 써요.

## 3.6 계약 3: 어댑터 인터페이스

interface ProviderAdapter {

  capabilities(): Capabilities                 // 지원 배포 형태 · 전략 · 고유 기능

  plan(ir: IR, target: Target): Promise<Plan>  // 생성 · 변경 · 삭제 목록

  apply(plan: Plan, ctx: DeployContext): Promise<ApplyResult>

  rollout(strategy: Strategy, ctx: DeployContext): Promise<RolloutResult>

  rollback(toVersion: string, ctx: DeployContext): Promise<void>

  destroy(target: Target): Promise<void>

  endpoints(ctx: DeployContext): Promise<string[]>  // 공개 URL

}

 

interface ObsAdapter {

  query(q: ObsQuery): Promise<NormalizedResult>  // 로그 · 메트릭 · 트레이스 · 프로파일

}

capabilities()가 있어서 추천·비용 엔진과 오케스트레이터는 "이 환경이 카나리를 지원하는가" 같은 질문을 어댑터에 물어보고 판단해요.

## 3.7 계약 4: 에이전트 도구 스키마 (예시)

{ "name": "propose_patch",

  "description": "배포에 필요한 코드 수정안을 diff로 제안한다. 적용은 사람 승인 후에만 된다.",

  "input_schema": { "type": "object",

    "properties": {

      "deployment_id": { "type": "string" },

      "goal": { "type": "string",

        "enum": ["sqlite_to_postgres", "externalize_config", "add_healthcheck", "add_otel"] } },

    "required": ["deployment_id", "goal"] },

모든 도구에 requires_approval 속성을 두고, true인 도구는 API 서버가 승인 이벤트 없이 실행하지 않아요. 가드레일이 프롬프트가 아니라 코드로 강제돼요.

# 4. 컴포넌트 상세

각 컴포넌트를 역할, 입력, 처리, 출력, 연결, 담당 기능 ID로 정리했어요.

## 4.1 CLI

| **역할** | 개발자가 터미널에서 배포를 실행하는 도구 |
| --- | --- |
| **입력** | 소스 폴더, 명령 (init, deploy, status, logs, rollback) |
| **처리** | 소스 업로드, API 호출, SSE 로그 수신. 로컬 러너 모드에서는 같은 파이프라인 정의를 로컬에서 실행 |
| **출력** | 배포 진행 상황, 로그, 결과 URL |
| **연결** | API 서버 |
| **기능 ID** | UI-02, CI-04 |

## 4.2 웹 대시보드

| **역할** | 사람이 판단하고 확인하는 화면 |
| --- | --- |
| **입력** | 사용자 조작 (승인, 편집, 선택, 롤백) |
| **처리** | 분석 리포트 표시, diff 승인, IR 편집, 추천 후보 선택, 플랜 미리보기·승인, 진행 상황·이력·관측 조회 |
| **출력** | 승인·편집·선택 결과를 API로 전달 |
| **연결** | API 서버 (REST + SSE) |
| **기능 ID** | UI-03, ANL-07, PAT-06·07, IR-03, REC-04, PRV-02, DEP-03·05, OBS-03, LOG-04 |

## 4.3 CI / Git

| **역할** | 코드 변경 시 자동 배포를 트리거 |
| --- | --- |
| **입력** | Git push 이벤트 |
| **처리** | 웹훅으로 API의 배포 생성 호출 |
| **출력** | 배포 요청 |
| **연결** | API 서버 |
| **기능 ID** | SRC-03, CI-01 |

## 4.4 외부 AI 도구

| 1–5 | 요청 · 락 | API가 배포를 만들고 즉시 ID를 돌려줘요. 오케스트레이터는 대상 환경 락을 잡고, 클라이언트는 SSE로 로그를 구독해요. |

| 12–14 | 환경 결정 | 추천·비용 엔진이 후보와 월 예상 비용을 제시하고, 사용자가 확정하거나 커스텀해요. |
| 15–20 | 빌드 · 계획 | 빌드 워커가 이미지를 만들어 레지스트리에 올리고, 프로비저닝 워커가 볼트에서 단기 자격증명을 받아 인프라 플랜을 만들어요. 사용자가 플랜을 승인해요. |
| 21–25 | 적용 · 검증 | 인프라 생성, DB 마이그레이션, 롤아웃(데이터 플레인이 레지스트리에서 이미지 pull) 후 검증 워커가 헬스체크와 스모크 테스트를 해요. |
| 26–27 | 완료 | 이력을 기록하고 락을 해제한 뒤 공개 URL을 돌려줘요. |

사전 개발 기간(킥오프 다음 날인 9/29부터 10/2까지, D1–D4)에 먼저 검증할 항목이에요. 위험이 크고 다른 작업의 전제가 되는 것부터 배치했어요. 각 PoC는 시간 제한을 두고, 성공 기준을 못 넘으면 대안으로 즉시 전환해요.

| **ID** | **PoC** | **검증 방법** | **성공 기준** | **실패 시 대안** | **일정** |

## 6.1 PoC 운영 원칙

- PoC마다 담당자 1명과 시간 제한(반나절~하루)을 정해요.

- 결과는 성공 · 실패와 관계없이 Notion에 "시도한 것, 결과, 결정"으로 기록해요. 실패해서 대안을 택한 기록이 곧 설계 결정 기록(ADR)이 되고, 팀 개발 점수의 "대안 · 논의 과정"이 돼요.

- D1의 P-01~03이 실패하면 전체 범위를 바로 재조정해요. 이 셋이 데모의 뼈대이기 때문이에요.

# 8. IR 예시

Express + SQLite로 만든 Todo 앱을 분석한 뒤 생성되는 IR 예시예요. 환경별 전용 옵션은 overrides에만 적어요.

services:

  web:

    build: ./

    port: 3000

    public: true

    healthcheck: /health

    env: [DATABASE_URL, JWT_SECRET]

    depends_on: [db]

    resources: { cpu: 0.5, memory: 512Mi }

    scale: { min: 1, max: 5 }

resources:

  db:

    type: postgres

    size: small

    migrate_from: sqlite://data.db

deploy:

  strategy: canary

  steps: [10, 50, 100]

overrides:

  gcp:

    web: { traffic_split: true }

# 9. 설계 결정 후보

팀 회의에서 대안을 비교하고 결정 이유를 Notion에 기록할 항목이에요. 팀 개발 점수의 "대안·논의 과정"에 해당해요.

| **결정** | **선택지** | **판단 기준** |
| --- | --- | --- |
| IaC 엔진 | Pulumi Automation API / Terraform CLI | 코드 내장 용이성 vs 레퍼런스 양 |
| 작업 큐 | Redis 기반 큐 / Temporal | 구현 속도 vs 재시도·복구 내장 |
| IR 형식 | Compose 확장 / 자체 스키마 | 친숙함 vs 표현력 |
| 온프레미스 연결 | SSH Push / 에이전트 Pull | 구현 난이도 vs 방화벽 뒤 서버 지원 |
| 온프레미스 런타임 | Docker Compose / k3s | 단순함 vs 롤링·자동 확장 지원 |
| 메인 클라우드 | GCP 먼저 / AWS 먼저 | Cloud Run이 가장 빠르게 붙음 |
| 샌드박스 방식 | 루트리스 BuildKit / 컨테이너 격리 / 마이크로 VM | 보안 수준 vs 구현 난이도 |
| 백엔드 언어 | TS / Go / Java | 팀원 역량, AI SDK·Pulumi 지원 |
| LLM | 모델·공급자 선택 | 코드 수정 품질, 토큰 비용 |
