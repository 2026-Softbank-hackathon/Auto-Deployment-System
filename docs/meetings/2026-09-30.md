- 나머지 P1/P2는 현재안 유지, 기능 명세 작성하며 조정

## 회의록 (발언자별)

### 1. 포커스: 타깃 · 문제 · 핵심 주장
**신은영 (안건 제안 배경)**
- 발표 시간이 짧아 "집중한 문제 / 보여줄 기술 / 이만큼 깊게 다뤘다"가 확 보여야 함. 지금은 너무 많이 다뤄서 안 보임
- 노선 둘 중 하나: ① 하나를 명확히 잡고 그 기준으로 의사결정 ② 현 설계에 더 붙여 압도적 완성도

**이정**: 어필 포인트 1~2개로. 지금까지 나온 아이디어 3개
- 조서현: 배포 후 마음에 안 들면 다른 벤더로 바로 전환 (클라우드 원클릭 전환, 차별성)
- 김민서: 플랫폼이 프로필 제공, PaaS처럼
- 이정: AI 분석 → IR → 사용자 개인 인프라 배포

### 2. 프로필 범위
- 김민서: 벤더별 리소스(ECS vs EC2, VPC · 네트워크, DB 등)를 AI · 규칙 · 입력으로 정하면 너무 퍼지고 원클릭에 아쉬움 → 벤더 리소스 구성을 미리 프로필화
- 신은영: 동의. 작년과 주제 같고 올해는 AI 강조. 원클릭 집중 → 프로필 AWS · GCP · Azure · 온프레미스 4개만, AWS는 ECS Fargate 등 서버리스 위주 자동화 (민서와 같은 이야기로 정리)
- 이정: 준비된 리소스만이면 유연성 부족 → P0/P1은 간단한 프로필, P1/P2에서 없는 모듈은 레지스트리 · 준비된 추가 모듈로 덧붙이기 → 전원 동의

### 3. 아키텍처: 사용자 계정 vs PaaS
- 이정: 절충안 설명. 컨테이너 PaaS면 일부 갈아엎고, 사용자 계정 인프라면 그대로
- 신은영 Q: 계정 정보를 받나, Terraform만 주나? → 이정: AWS 가입 후 발급한 키를 등록 → 소스 올리면 IaC로 세팅
- 김민서 Q: 우리 서버가 아니라 사용자 계정? → 이정: 맞음, 사용자가 본인 인프라 관리 가능이 차별점
- 이정 근거: 작년 수상팀 대부분 PaaS(구현 쉬움), 올해는 다들 작년 참고할 것 → 독창성 · 유연성 · 가용성. 원클릭 전환도 사용자 계정 쪽이 자연스러움 (PaaS는 한 클라우드에 종속, 사용자 키 여러 개면 중립 IR로 이동 쉬움)
- 김민성 Q: 리스크? → 이정: 시연 시간. 인프라 구성 지연(몇 분) → 앞부분 실행 + 완성된 앱 접속 확인으로 시연
- 김민서: 이 규모 클라우드 구성 경험 없어 견적 X, 일정 촉박 우려 → 이정: 챌린징, 가능하지만 "무조건"은 리스크 / 신은영: 갈아 넣으면 가능 / 김민서: 가능하다면 OK
- 김민서 (PaaS 벤더 전환): 범위는 AWS + 온프레미스, 이미지 빌드라 컨테이너 방식 그대로. GCP · Azure 전환하려면 거기에도 우리 인프라가 있어야 함. 포터빌리티 = 동일 이미지 완벽 호환
- 이정: 그게 나을 수도. IR → 어댑터 → Terraform은 그대로, 평가 기준상 큰 차이 없을 것 → 신은영 동의
- 신은영: 위험 없으면 각자 계정이 좋지만 데모 때문에 PaaS도 나쁘지 않음, 프로필 있으면 벤더 맞춰 빌드만 → 쉬움 / 이정: 차이는 사용자에게 인프라 관리 권한 주는 정도
- 신은영: DB 마이그레이션(P1) 시 고객 DB 분리 필요 → 생성 시간 길어져 어느 방식이든 같아짐. DB까지 목표면 시작해 두고 따로 보여주기
- 이정: 공용 RDS + 스키마 분리 안도 있지만 확장성 트레이드오프
- 김민서: 작년 최우수는 PaaS 아니고 인프라 구성 방식, 데모 앱 하나에 정확히 호환 (확실하진 않음) → 이정: 인프라 직접 구성이면 사용자 계정 방식이 맞음, 시연이 애매
- 김민서: 시연에서 인과관계 설명 걱정 → 이정: 이미지 digest 로그로 동일성 증명, 매끄럽진 않음, 로깅 · 대시보드로 확인 가능

### 4. 데모 방식
- 김민서: 배포 갱신 + 클라우드 ↔ 온프레미스 전환을 매끄럽게
- 신은영: AWS에 v1 미리 배포 → v2 반영 → 온프레미스나 다른 클라우드로 전환
- 김민서: 전환은 앞단 프록시(Cloudflare 등) 하나로, DNS 수정보다 쉬움
- 이정: 동일 환경 미리 만들고 전환 버튼 → 트래픽 전환 시연, 3분 내 가능한지는 미지수
- 신은영: 작은 앱이면 온프레미스 전환 가능, 온프레미스 → 클라우드는 느림, 반대는 가벼운 앱
- 김민서: 샘플 앱은 static으로(평가 대상 X), Spring 빌드는 무리
- 신은영: static은 빌드할 게 없어 보여줄 게 없음 → 가볍더라도 빌드되는 앱
- 이정: PoC는 HTML 하나였음
- 김민서: 인프라 구축 결과보다 "이미지 배포 갱신 + 전환"이 나음 → **1차 픽스**
- 아키텍처 결론: 일단 사용자 키 방식, 이정 PoC, 운영진 불가 시 PaaS. 김민서: 불가여도 배포 갱신 · 전환은 보여줄 수 있음
