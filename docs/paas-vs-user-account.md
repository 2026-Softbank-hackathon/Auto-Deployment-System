# PaaS vs 사용자(개인) 계정 전용 인프라 — P0 방식 비교 (2026-09-29 밤)

노션 "PaaS vs 개인 계정 인프라" 페이지와 같은 내용. **9/30 회의 결론은 "일단 사용자 계정, 운영진 불가 시 PaaS"** (아래 5번 절충안은 이정 개인안이었고 회의에서 채택되진 않음).

## 0. 배경
- 사용자 계정에 VPC · ALB · ECS · RDS를 처음부터 만들면 10분 이상 (RDS만 5~10분)
- 최종 데모 3분 (통역 시간 제외), 실제 배포 모습 필수, 목업은 명시
- 채점: 데모 30 / 클라우드 활용 30(환경 차이 흡수 · 이식성 · **각 클라우드 고유 기능**) / 팀 20 / 독창성 10 / AI 10
- 테마: "코드를 자동으로 변경하면서 적절하게 인프라 환경까지 구축", 예시 "SQLite → 적절한 설정의 RDS"
- 운영진 개인 문의(9/29 22시): ① 발표 전 시작한 실제 배포로 완료를 보여줘도 되나 ② 공통 인프라 사전 구축 + 앱 리소스만 생성도 "실제 배포 시연"인가 ③ PaaS 형태도 적절한가 → **답변 대기**

## 1. 공통 전제
- 분석 → IR → 1회 빌드(같은 digest) → 어댑터까지는 동일
- "도커 이미지 + 메타데이터" = 우리 "이미지 + IR" (Heroku app.json, Score, OAM/KubeVela, Cloud Native Buildpacks 계열)
- 차이는 하나: **배포 대상 인프라가 누구 것이고 언제 만들어지나**

## 2. 입장 A — PaaS P0
**정의**: 여러 기반 위에서 도는 AI PaaS. 우리가 AWS · 온프레미스에 실행 기반을 미리 IaC로 깔고, 앱은 같은 이미지 + IR로 올림. 백킹 서비스(DB 등)는 기반마다 고유 서비스로 번역
**기반 (1회 구축, 상시)**
- AWS: VPC, 공용 ALB(`*.aws.도메인` + ACM), ECS Fargate, Cloud Map, 공용 RDS, Secrets Manager, CloudWatch, ECR
- 온프레미스: Intel Mac VM, Docker, Traefik, cloudflared(`*.onprem.도메인`), Postgres 컨테이너, 에이전트
- (P2) GCP: Cloud Run + Cloud SQL
**앱 배포 (앱 단위 리소스만)**
| | AWS | 온프레미스 |
|---|---|---|
| 실행 | ECS 서비스 + 태스크 정의 | Compose 서비스 |
| 라우팅 | 타깃 그룹 + 리스너 규칙 | Traefik 라벨 |
| DB | 공용 RDS 안 앱 전용 DB · 유저 | PG 컨테이너 안 앱 전용 DB · 유저 |
| 시크릿 | Secrets Manager | 에이전트 env 주입 |
| 로그 | CloudWatch | Docker 로그 |
| 격리 | 앱별 SG · IAM 역할 · 리소스 제한 | 앱별 Docker 네트워크 · 리소스 제한 |
- 앱 스택도 Terraform → plan 승인 유지
- PaaS에서 공용 인스턴스 + 앱별 DB는 업계 표준 (Heroku 저가 플랜, Neon, Supabase)
**v5.4.1 대비**: 분석 · IR · 빌드 · 게이트 · DB 변환 · 큐/락 · UI 유지 / 프로필 → "기반 + 앱 배치 템플릿", 프로비저닝 = 앱 리소스만, P1 애드온 → 플랫폼 백킹 서비스, **P2 사용자 정의 모듈 거의 불가**
**채점**
- 데모: 전 과정 라이브 (SQLite → Postgres 포함), 운영진 답변 무관
- 클라우드 활용: 같은 digest · IR로 두 기반, env 계약(12-factor), `db: postgres` → AWS RDS / 온프레미스 컨테이너 번역(애드온 모델), 기반 IaC 코드 · plan 제시. 약한 건 앱별 맞춤 구성뿐
- 독창성: 비슷한 PaaS 많음 → AI 분석 · 코드 변환, 온프레미스 포함 여러 기반, 환경 전환으로 보완
- **환경 전환이 쉬워짐** (두 기반 상시) → P1 하이라이트 가능
**약점 · 대응**: "또 하나의 PaaS"(→ 차별점 전면), "인프라 구축" 인상 약함(→ 기반 IaC · 앱 plan), "자기 계정엔?"(→ 전용 인프라 P1 로드맵), 멀티테넌트 격리(→ SG · IAM · DB 유저 · 제한), 사용자 정의 모듈 불가(→ 애드온 카탈로그), 상시 비용(월 수십 달러), 3분 빠듯(→ 캐시 · 작은 앱 · 헬스체크 단축 · 리허설)
**데모 시간 추정**: 분석 20~40초 + 빌드 40~90초 + ECS 첫 배포 1~2분(온프레미스 30초 병렬) → 2~3분. "가능" 수준

## 3. 입장 B — 전용 인프라 P0
**정의**: 배포마다 앱에 맞춘 AWS 인프라(ALB · ECS · RDS 등)를 사용자 계정에 Terraform으로 **한 번에** 생성 (인프라/앱 단계 분리 안 함). 데모는 팀 계정이 사용자 계정 역할
| 구성 | 예상 시간 |
|---|---|
| DB 없는 앱 | 5~7분 (빌드 1~2 + ALB 2~3 + ECS 1~2) |
| RDS 포함 | 12~17분 |
| 재배포 | 1~2분 |
| 온프레미스 | 1분 안쪽 |
(팀원 PoC 실측: Terraform AWS cold ~4.3분, warm ~2.1분 — RDS · ALB 포함 여부 불명)
**채점**: 데모 불리(앞부분 라이브 + 미리 시작한 배포, 운영진 답변 의존) / 클라우드 활용 **가장 강함**(plan에 실제 리소스, IR에서 크기 · SG · IAM · RDS 설정) / SQLite → RDS 문자 그대로 일치하나 라이브 불가 / 독창성 약간 유리
**제품 장점**: 소유권 · 종속 없음, 격리, 비용 투명성(plan 전 월 비용 → 비용 엔진 CST-03), 사용자 정의 모듈 가능, 스택 하나 · apply 한 번
**약점 · 대응**: 3분 초과(연출), **개발 반복 속도**(생성 12~17분 + RDS 삭제 5~10분 → DB 없는 앱으로 반복), apply 실패 복구 느림(destroy 후 재시도), VPC 한도 리전당 5개(기본 VPC 사용), 앱당 대기 비용 월 $40~55(TTL 자동 삭제), 환경 전환 어려움(10분+)

## 4. 비교
| 관점 | PaaS P0 | 전용 인프라 P0 |
|---|---|---|
| 데모 30 | **유리** | 불리 |
| 이식성 | 동등 | 동등 |
| 클라우드 고유 기능 | 충분 | **더 강함** |
| SQLite → DB | 라이브 가능(공용 인스턴스) | 적절한 RDS, 라이브 불가 |
| 벤더 대응 | 동등 | 동등 |
| 독창성 10 | 약간 불리 | 약간 유리 |
| 개발 반복 속도 | **빠름** | 느림 |
| 환경 전환 | **쉬움** | 어려움 |
| 사용자 정의 모듈 | 불가 | 가능 |
| 소유권 · 격리 | 불리 | 유리 |

**해석 정정**: 킥오프 "各社環境(각 회사의 환경)"은 사용자 회사 환경이 아니라 **각 클라우드 벤더 환경**일 가능성이 높음 → 사용자 계정 방식의 채점 근거로 쓰지 않음. 온프레미스는 두 방식 모두 우리 머신

## 5. 이정 개인 절충안 (회의 미채택, 참고)
- PaaS냐 아니냐를 **프로필 선택**으로: 공용 실행 환경 프로필(PaaS 모드) + 전용 인프라 프로필. AWS 프로필 모듈 하나 추가 비용
- P0 PaaS / P1 환경 전환 + 전용 인프라(plan · 결과 · 문서) / P2 사용자 정의 모듈 · GCP
- 전용 인프라 P0 조건: ① 운영진이 미리 시작한 배포 허용 ② Terraform 모듈 수요일 중 단독 apply 성공

## 6. 검토 후 접은 안
| 안 | 접은 이유 |
|---|---|
| 베이스 층 / 앱 층 분리(v5.5) | 복잡, 명세 불일치 · 유휴 자원, 앱 없이 환경부터 만드는 흐름 부자연스러움 |
| 사용자 계정 안 공용 RDS | 격리 깨짐, "적절한 RDS"와 어긋남 |
| 인프라/앱 apply 단계 분리 | 이득 1~2분 대비 복잡 |
| Aurora DSQL (생성 수 초) | 트리거 · PL/pgSQL · 확장 · 임시 테이블 X, DDL 트랜잭션당 1개, OCC 재시도, IAM 토큰 접속 → Drizzle 호환 검증 필요, 보류 |
| 미리 시작한 배포로 완료 화면 | 운영진 답변 대기 (데모 연출 후보) |
| CloudTrail 세션명 · default_tags로 "우리 도구가 만든 인프라" 증명 | 두 층 분리 폐기로 필요성 감소, 필요 시 재사용 |
