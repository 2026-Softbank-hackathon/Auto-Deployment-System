오늘 원활한 진행을 위해 회의 안건 정리해 보았습니다!

1. Primary Target User / 해결 문제 / 데모에서 증명할 핵심 기술 주장
• 논의 포인트:
우리의 Primary Target User를 누구로 볼지
사용자가 겪는 Deployment 문제 중 어떤 문제를 핵심으로 해결할지
데모에서 어떤 기술적 주장을 가장 명확하게 증명할지
AWS ↔ On-Prem 환경 간 Portability / 전환을 프로젝트의 핵심 차별점으로 가져갈지
• 회의에서 결정/확인할 것:
누구의 어떤 문제를 해결하는 시스템인지, 데모에서 무엇을 증명할지 한 문장 수준으로 합의

2. P0 MVP 범위와 성공 기준
• 논의 포인트:
P0를 단일 Monolith HTTP Application으로 제한할지
소스 입력 → IR 생성·검증 → Image 1회 Build → 동일 Digest로 AWS·On-Prem 배포 → URL 반환 → Health Check 성공을 P0 핵심 흐름으로 확정할지
AWS / On-Prem 실제 실행 환경과 동일 Image Digest 시연 방식을 어떻게 가져갈지
DB 전환, MSA, Blue-Green/Canary, 자동 Failover 등의 기능은 P0 이후로 둘지
• 회의에서 결정/확인할 것:
P0에 반드시 들어가는 기능과 P0 완료 조건을 명확하게 확정

3. IR / Environment Profile / Adapter의 역할과 책임
• 논의 포인트:
IR에는 어디까지 Application Requirement를 표현할지
http / worker / static / job 등의 서비스 유형과 Resource Requirement를 IR에 어떻게 담을지
Environment Profile을 aws-ecs-basic / onprem-docker-basic처럼 환경별 검증된 Infrastructure 골격으로 정의할지
Profile이 지원하는 Service Type / Capacity를 어떤 수준으로 표현할지
Adapter가 Infrastructure를 새로 설계하는 구조인지, 선택된 Profile/Terraform Module에 IR 값을 Mapping하는 구조인지
P0는 단일 서비스만 구현하더라도 IR 자체는 여러 Service를 담을 수 있게 설계할지
• 회의에서 결정/확인할 것:
IR → Profile → Adapter → Terraform 사이의 책임 경계를 팀 전체가 같은 의미로 이해하도록 정리

4. AI / Rule / 사용자 입력의 역할 분담
• 논의 포인트:
Repository 및 Manifest에서 자동 감지할 영역과 AI가 판단할 영역의 경계
IR을 AI가 전체 생성할지, 감지·사용자 입력 후 남은 애매한 부분만 AI가 보완할지
Dockerfile이 없을 경우 규칙/Template 기반 생성 → 처리되지 않을 경우 AI 순서로 갈지
Profile 추천/선택에 AI를 어느 정도 사용할지
한 번 생성한 IR을 저장하고 재배포 시 AI를 다시 호출하지 않는 방향으로 갈지
• 회의에서 결정/확인할 것:
AI가 반드시 필요한 판단과 deterministic하게 처리할 영역을 구분

5. P0 이후 기능의 우선순위와 환경 전환 범위
• 논의 포인트:
P1에서 SQLite + Drizzle 기반 Sample → PostgreSQL 전환 시나리오를 우선할지
DB 전환 시 사용자 원본은 유지하고 Deployment용 복사본만 변경하는 방향으로 갈지
Logging / Rollback / Secret / Deployment Lock / Queue / Idempotency 등의 기능을 어느 단계까지 가져갈지
환경 간 전환을 구현한다면 동일 Digest 대상 환경 배포 → Health Check → Traffic Switch → 기존 환경 정리 흐름을 사용할지
고정 Domain + Traffic Switch, On-Prem 장애 시 AWS 자동 전환, Blue-Green/Canary 등을 P2 후보로 둘지
• 회의에서 결정/확인할 것:
P0 이후 P1/P2에서 무엇을 먼저 구현할지 우선순위를 정하고, 환경 전환 기능을 실제 구현 범위에 어디까지 포함할지 확인

6. Repository 구조와 공통 Schema 관리 방식
• 논의 포인트:
Multi-repo로 Component/담당자별 Repository를 분리할지
Monorepo + 폴더별 담당자 방식으로 갈지
IR Schema / API Type처럼 여러 Component가 함께 사용하는 정의를 어떤 방식으로 관리할지
• 회의에서 결정/확인할 것:
구현 시작 전에 Repository 구조와 공통 Schema 관리 방식을 확정

7. 역할 분담 및 담당 영역 확정
• 논의 포인트:
P0 기준으로 필요한 작업 영역을 나누고 각 담당자를 어떻게 배정할지
IR / Analyzer / AI / Deployment Engine / AWS·On-Prem Adapter / Infra / Web·API / Demo·문서화 등 실제 구현 영역별 담당을 어떻게 가져갈지
한 사람이 단독으로 맡을 영역과 여러 명이 같이 작업해야 할 영역을 구분할지
공통 Schema나 Integration처럼 여러 파트가 맞물리는 작업의 담당/조율 방식을 어떻게 할지
오늘 확정한 P0 우선순위에 맞춰 각자 바로 시작할 첫 작업을 무엇으로 할지
• 회의에서 결정/확인할 것:
팀원별 1차 담당 영역과 바로 착수할 작업을 정해서 회의 이후 개발을 바로 시작할 수 있는 상태로 만들기
