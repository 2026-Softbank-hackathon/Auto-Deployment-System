입력: 팀원 문서 `ARCHITECTURE_IMPROVEMENTS_v1.md`, `ARCHITECTURE_v2_ONBOARDING.md` (docs/reference/team/)
- v4/v4.1: 전체 + 파이프라인 확대(소스 업로드 → AI 분석 → IR → 어댑터 → 인프라) 다이어그램 2종
- Q&A로 정리된 것
	- Terraform vs OpenTofu → **Terraform** (자료 · 숙련도), OpenBao → 과함, **SOPS + age + Postgres AES-GCM**
	- 맥북 amd64 빌드 → 이정은 **Intel Mac**이라 문제 없음 → amd64 단일
	- CLI · MCP · CI는 옵션, Slack 봇 제외, 웹 먼저
	- GCP · Azure 박스 제거 → 작은 "프로필 확장(P2)"로만
	- 33 테이블 → 22 축소 권고 (미결)
- **민서님 의견 반영**: 프로필 = 환경별로 미리 검증한 인프라 골격 (서비스 유형별 아님). IR은 앱 요구만, 어댑터는 매핑만
- **서현님 의견 반영**: 레퍼런스 조사(Karmada, VMware HCX, Coolify, Dokploy, AWS Copilot), DB 전환은 배포본만 규칙 변환 + raw SQL 경고, 환경 전환 = 차별점(P2)
- 이정 의견 → "프로필에 딱 안 맞는 소스"도 배포 가능해야 → **빠진 요소 먼저 알림 → 사용자가 추가/제외 선택**, 추가는 **커스텀 모듈**(골격 위에 얹음, 골격 output → 모듈 input, 모듈 output → 앱 env)
- 모듈 출처 순서: ① 팀 애드온 ② Registry 허용 목록(AI는 입력값만) ③ 사용자 작성 ④ AI 생성(최후) — "AI가 인프라를 설계하지 않는다"는 표현은 부정확해서 "AI 개입 범위를 단계별로 제한"으로 정정
- 배포 대상 선택은 **필수 입력, 기본값 없음**
- v5.4에서 전체 재검토 → 오류 12개 수정
- v5.4.1: 팀원 제안으로 **확장 모듈 P1 = 팀 검증 애드온 / P2 = 사용자 정의(②~④)**
- 비용 엔진 P1 vs P2 → 미결 (CST-03이 M, 평가 "비용 효율성")

## 4. 데모 시간 문제 → PaaS vs 사용자 계정 (9/29 저녁)
- 팀원 문제 제기: 전체 인프라 생성 + 빌드는 3분 불가, RDS 포함이면 사실상 불가
- 검토 1 — **베이스 층 / 앱 층 분리**(v5.5 안): 첫 배포 때 VPC · ALB · 클러스터 생성, 이후 앱 층만 → **폐기** (복잡, 앱마다 명세 달라 불일치, 앱 없이 환경부터 만드는 흐름 부자연스러움)
- 검토 2 — **사용자 계정 안 공용 RDS** → **폐기** (격리 깨짐, "적절한 설정의 RDS"와 어긋남)
- 검토 3 — **Aurora DSQL**(생성 수 초) → 보류 (트리거 · 확장 미지원, DDL 제약, IAM 토큰 접속)
- 검토 4 — 인프라 · 앱 단계 apply 분리 → **안 나눔** (이득 1~2분 대비 복잡도)
- 운영진 개인 문의 (9/29 22시, 일본어 · 한국어): ① 발표 전 시작한 실제 배포로 완료 보여줘도 되는지 ② 공통 인프라 사전 구축 인정 여부 ③ PaaS 형태의 적절성 → **답변 대기**
- 운영진 문의 후 PaaS를 깊게 파 봄 → "도커 + 메타데이터"는 사실상 "이미지 + IR"과 같음, 차이는 배포 대상 인프라의 소유 · 생성 시점뿐
- **"각 회사의 환경"(各社環境) 해석 정정**: 사용자 회사 환경이 아니라 각 클라우드 벤더 환경일 가능성이 높음 → 사용자 계정 방식의 채점 근거에서 제외
- 결론(개인 절충안): **P0 PaaS + P1 전용 인프라(사용자 계정)**, 판단 기준 = ① 운영진 답변 ② Terraform 모듈을 수요일 중 단독 apply 가능한지 → `docs/paas-vs-user-account.md`
- 그러나 **9/30 회의에서는 "일단 사용자 계정 방식, 불가 답변 시 PaaS"로 결정** (회의록 참고)
